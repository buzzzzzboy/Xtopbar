# 工作列小工具設計

日期：2026-11-27

## 目標與原因

讓使用者把常用的小資訊、小操作直接放到工作列上，不必打開開始選單或其他 App。第一批做三種小工具：

1. **正在播放**：瞄一眼歌名，順手播放／暫停
2. **CPU／記憶體**：隨時看到系統負載
3. **開始選單資料夾**：把開始選單裡的某個資料夾放到工作列，點一下就能開裡面的 App

位置由使用者決定，例如開始按鈕的左邊或右邊、App 條的開頭或結尾。

成功的樣子：
- 在設定裡打開「正在播放」，選「開始按鈕右邊」，工作列上就出現一顆膠囊。滑鼠移到中間那塊立刻亮起，點一下就能暫停；兩端的鍵可以切歌
- App 開得再多，小工具都不會被擠掉，也不會跟著標籤捲走。App 條會照常合併或縮窄，讓出小工具佔的位置

## 目標／非目標／反目標

- **目標**：三種小工具、六個固定槽位、在設定裡和右鍵選單裡調整位置
- **非目標（這版不做）**：直接在工作列上拖曳小工具（以後可以在槽位的基礎上加）、放到兩個 App 標籤中間、第三方或自訂小工具、每塊螢幕各自一套配置
- **反目標**：
  - 小工具和 App 標籤的點擊、拖曳互相搶，例如拖標籤時誤觸小工具
  - 小工具讓 App 條的寬度來回抖動
  - 沒開小工具的使用者有感覺到任何變化，包括寬度、效能和外觀

## 限制

- macOS 26 以上，Apple Silicon（arm64），只用 Liquid Glass（`GlassBackdrop`／`GlassPill`），不寫舊系統的替代畫法
- 點擊判定一律走現在的窗口層命中測試：用保留 id 把命中範圍上報到 `catalog.tabFrames`（同 `AppCatalog.startButtonID`），在 `AppCatalog` 的按下處理裡判斷，不能靠 SwiftUI `Button` 自己收點擊
- 寬度一律用估算值（同 `TaskbarLayout.Metrics.fixed`、`AppCatalog.preferredWidth`），不能等 SwiftUI 量回來，否則條寬會「量完、重排、再量」來回抖
- 播放控制沿用 `NowPlaying`（媒體鍵＋分散式通知），不用 MediaRemote 或 Apple Event

## 做法比較

| 做法 | 取捨 | 結果 |
|---|---|---|
| **A. 固定槽位，在設定裡選位置** | 做起來穩，點擊判定沿用開始／搜尋按鈕那套；但只能放在預先定好的幾個位置 | **使用者選了這個** |
| B. 在工作列上直接拖曳擺放 | 最直覺；但拖曳要能跨過幾段玻璃，還要跟標籤拖曳排序分開判斷，工作量約 A 的兩倍，也比較容易誤拖 | 不做，以後可以在 A 的槽位上加 |

## 槽位

```
[1] (⊞ 開始) [2] (🔍 搜尋) [3] ┃把手┃ [ [4] App 標籤…… [5] ] [6]
```

| # | 代號 | 位置 | 外觀 |
|---|---|---|---|
| 1 | `beforeStart` | 開始按鈕左邊，整條最左 | 條外獨立玻璃膠囊 |
| 2 | `afterStart` | 開始和搜尋之間 | 條外獨立玻璃膠囊 |
| 3 | `beforeBar` | 搜尋右邊、把手左邊 | 條外獨立玻璃膠囊 |
| 4 | `barLeading` | App 條玻璃裡的開頭 | 畫在條的玻璃裡，不另外墊玻璃 |
| 5 | `barTrailing` | App 條玻璃裡的結尾 | 同上 |
| 6 | `afterBar` | App 條右邊，整條最右 | 條外獨立玻璃膠囊 |

- 開始或搜尋按鈕關掉時，相鄰的槽直接靠攏，例如沒有開始按鈕時，1 和 2 會緊挨著，看起來就是同一個位置
- 同一個槽放了好幾個小工具，就照設定裡的順序由左到右排
- 條外的膠囊高度等於條高，彼此和開始圓之間的縫沿用 `detachedStartGap`
- 4、5 號槽**不在 ScrollView 裡**：固定在條的玻璃內兩端，標籤在它們中間捲動，捲動兩端的漸層也只蓋在標籤那段
- 調大小的把手維持在「條外最後一顆東西」和 App 條之間。整條沒有 App 標籤、只剩條外的東西時，比照現在只剩開始／搜尋圓的情況
- **沒有任何 App 標籤時**（*我的決定*）：條的玻璃本來就不畫，4 號槽的小工具改畫成條外膠囊、排在 3 號槽後面，5 號槽的排在 6 號槽前面。`TabBarController.hasBarItems` 要把「至少有一個看得見的小工具」算進去（正在播放隱藏時不算），否則「隱藏空工作列」會把小工具一起藏掉
- **和「背景執行」小方塊的關係**（*我的決定*）：`BackgroundFolderController` 是貼在條尾巴的獨立視窗，6 號槽排在它**左邊**，也就是小方塊永遠在最外側。`relayout()` 為小方塊讓出的 `tailWidth` 不變，6 號槽的寬度算在條的面板裡。資料夾小工具不顯示數字，和小方塊的「2×2＋數字」區分開。資料夾卡片和背景網格互斥，開一個就先收另一個

## 三種小工具

### 正在播放

- **版型**：膠囊分三段

  ```
  ( ⏮ │  [封面] 歌名……  ▶︎  │ ⏭ )
        └──── 這整塊都是播放／暫停 ────┘
  ```

- **中間是播放／暫停區**：封面（Apple Music 用 App 圖示）＋歌名（寬度跟著歌名走，最寬 140pt，超過就截斷）＋緊跟在歌名後面的播放／暫停狀態圖示。指標一進入這一塊，整塊**立刻**亮起懸停底（沒有延遲、沒有動畫等待），點哪裡都是切換播放（`NowPlaying.playPause()`）
- **兩端是 ⏮／⏭**：各一顆小鍵，寬度約條高的一半、高度等於條高，各自有懸停底，點了呼叫 `NowPlaying.previous()`／`next()`。還沒有曲目時這兩顆變灰、不可按（同 `NowPlayingBar` 現在的做法）
- **只顯示圖示樣式**：一樣是三段，中間拿掉歌名，只留封面和狀態圖示；歌名和歌手放進懸停提示
- **沒有浮窗**。右鍵選單最上面放「開啟 Spotify／音樂」，下面是共用的「移到」等項目
- **沒有播放器在跑**（依 `prefs.nowPlayingSource`：自動時 Spotify 和 Music 都沒開；固定來源時那個 App 沒開）：整顆隱藏，寬度歸零
- 播放器開著但還沒有曲目：縮成「播放器圖示＋▶」一小顆，整顆都是播放鍵，不畫 ⏮⏭
- `NowPlaying` 現在只聽 App 結束（`didTerminate`）和播放器自己的通知，**不聽啟動**。要加上 `didLaunchApplicationNotification` 的監聽，播放器一開就讓小工具出現並重算版面

### CPU／記憶體

- **外觀**：膠囊裡兩組「標籤＋百分比＋迷你橫條」，例如 `CPU 23%` 和 `記憶體 61%`，數字用等寬字體，數字變了寬度也不跳。只顯示圖示樣式下改成兩條直立的迷你條，數字放進懸停提示
- **更新**：共用一個取樣器，每 2 秒取一次。只有至少一個 CPU／記憶體小工具開著時才取樣，全部關掉就停
  - CPU：`host_statistics(HOST_CPU_LOAD_INFO)` 前後兩次 tick 的差值
  - 記憶體：`host_statistics64(HOST_VM_INFO64)` 的（active + wired + compressed）÷ 實體記憶體，跟「活動監視器」的「已使用記憶體」口徑一致
- **點擊**：打開「活動監視器」（`com.apple.ActivityMonitor`）
- 超過 80% 時數字和橫條改用警示色（系統橘），不閃爍

### 開始選單資料夾

- 每個資料夾小工具指向一個 `StartFolder.id`，同時可以放好幾個資料夾
- **外觀**：圖示沿用開始選單的 `FolderTile`（目前是 StartMenuView 裡的 `private`，用 `StartLayout` 縮放，要拆成共用元件並改吃 `TTLayout`），也就是 2×2 的 App 縮圖。圖示＋名稱樣式下旁邊加資料夾名稱，只顯示圖示樣式下只有圖示，名稱放進懸停提示
- **點擊**：在小工具上方（停在頂部時是下方）跳出卡片，列出資料夾裡的 App（圖示＋名稱的格子），點一個就開啟，同時收起卡片。點卡片外面或再點一次小工具也會收起。卡片內容和開始選單裡資料夾展開的 `padCard` 一樣，但只能開 App，不能在這裡改名或拖曳。`padCard` 現在和改名的 TextField、`reorderGrid` 拖曳綁在一起，要拆出唯讀版本
- 資料夾是空的：卡片寫「資料夾是空的」，加一個「在開始選單中編輯」的按鈕
- 資料夾在開始選單裡被刪掉：對應的小工具一起移除
- 開始選單裡資料夾的右鍵選單多一項「放到工作列」，加到 `afterBar` 槽的最後

## 設定與資料

- `Preferences.taskbarWidgets: [TaskbarWidget]`，UserDefaults key `taskbarWidgets`，存成 JSON：
  ```swift
  struct TaskbarWidget: Codable, Identifiable, Equatable {
      var id = UUID()
      var kind: Kind            // .nowPlaying / .systemStats / .folder(UUID)
      var slot: TaskbarWidgetSlot
  }
  ```
  陣列順序就是同一個槽裡由左到右的順序
- 預設是空陣列：升級上來的使用者看不到任何變化
- 正在播放、CPU／記憶體各最多一個，資料夾一個資料夾最多一個
- **設定視窗**：「Dock 與開始選單」頁新增一段「工作列小工具」：
  - 一列一個已加入的小工具：名稱、槽位下拉選單、上移、下移、移除
  - 「新增小工具」選單：正在播放／CPU 與記憶體／資料夾 ▸（列出開始選單的資料夾），已經加過的選項變灰
- **右鍵小工具**：「移到」▸ 六個槽位（目前的打勾）／「在設定中調整…」／「從工作列移除」。右鍵小工具時不顯示整條的右鍵選單

## 寬度與版面

- 每個小工具提供一個估算寬度（未縮放的 pt），寫成純函式，跟 `TaskbarLayout` 一樣不碰 AppKit
- 條外槽（1、2、3、6）和條內槽（4、5）的寬度都要算進兩條路徑：
  - 決定合不合併的 `layoutMetrics().fixed`（純估算）
  - 條寬 `AppCatalog.preferredWidth`：拿到 SwiftUI 實測的 `contentWidth` 後就改用實測值，但實測只量 ScrollView 裡的標籤，所以小工具的寬度在**實測和估算兩種情況都要另外加**
- 現在到處用 `TTLayout.detachedStartWidth` 代表「條左邊拆出去的東西」，包括 `bar` 的寬度、捲動可見範圍、沒有標籤時的 `preferredWidth`。要改成一個能算出「條左邊總寬、條右邊總寬、條內兩端總寬」的版面描述，而不是在各處加數字。這是這次改動裡最大的一塊
- 正在播放的寬度**跟著歌名長短走**（使用者要求，2026-11-27）：用 `NSFont` 量歌名，最寬 140pt，超過就截斷。換歌會重算一次版面，這是使用者接受的代價
- 沒有曲目時縮成「播放器圖示＋▶」一小顆（使用者選定），不畫用不到的 ⏮⏭
- 正在播放隱藏時寬度算 0；播放器開或關會重算一次版面，這是可以接受的
- 介面縮放一律走 `TTLayout.s()`／`TTLayout.font()`

## 點擊與互動

- 每個小工具用保留 id 上報命中範圍：`__widget__<uuid>`。正在播放另外上報兩個子按鈕 `__widget__<uuid>__prev`、`__widget__<uuid>__next`，判斷時先比子按鈕，沒中才算中間的播放／暫停區
- `AppCatalog` 的按下處理順序：把手 → 開始 → 搜尋 → **小工具（先比子按鈕）** → App 標籤
- 拖曳 App 標籤時，指標掃過小工具不亮懸停底，放開時落在小工具上也不算點擊（比照現在 `catalog.drag != nil` 的處理）
- 右鍵：整條的右鍵選單是 SwiftUI `.contextMenu`，只有 `TabBarController.openTaskbarMenu` 回傳 false 時才出現。小工具的右鍵要在 `openTaskbarMenu` 裡攔下來，改走 `TaskbarMenu` 那套自訂選單；那裡的保留 id 集合也要加上小工具
- 浮窗（只有資料夾卡片）用 `FloatingPanel`，彈出方向跟著停靠位置走。開了浮窗時，條不自動隱藏，比照開始選單的處理
- 浮窗開著時點另一個小工具：先收起舊的再開新的。同一時間最多開一個

## 多螢幕

- 開了「在所有螢幕上顯示」時，**每條都顯示同一套小工具**（跟開始按鈕一樣）。浮窗從被點的那條彈出
- CPU／記憶體的取樣器全域只有一個，各條只是顯示同一份數字

## 交給建造者決定

- 槽位、小工具在 SwiftUI 裡的拆法、檔案怎麼分（建議新增 `TaskbarWidgets.swift` 放模型與估寬，`SystemStats.swift` 放取樣器）
- 膠囊內的細部間距、圖示大小，以和現有 `AppTab` 視覺一致為準
- `--test-pins` 一類的自我測試要不要加小工具寬度的樣例
